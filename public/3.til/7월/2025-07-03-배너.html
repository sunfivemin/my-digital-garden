🧠 상세 학습 내용

📍 주제 1: 메인 페이지 배너 기능 흐름 및 폴더 구조 설명

✅ 1. 도입: 왜 이렇게 폴더를 나눴는가?

이번 프로젝트에서 저는 배너 데이터를 MSW로 Mock 처리하고, 이 데이터를 메인 페이지에서 슬라이드 배너 UI로 렌더링하는 구조를 설계했습니다.
핵심 목표는 유지보수 가능한 구조와 역할별 분리였습니다.

✅ 2. 폴더 구조 설명

src/
├── api/                   # API 요청 함수 정의
│   └── banner.api.ts
├── mock/                  # MSW를 활용한 가짜 데이터 정의
│   └── banners.ts
├── models/                # 타입 정의 (Banner 인터페이스)
│   └── banner.model.ts
├── hooks/                 # 커스텀 훅 모음
│   └── useMain.ts
├── components/
│   └── common/
│       └── Banners/
│           ├── Banners.tsx        # 전체 배너 슬라이더 컴포넌트
│           ├── BannerItem.tsx     # 단일 배너 아이템
│           └── banner.css.ts      # Vanilla Extract 스타일

✅ 3. 전체 흐름 요약

📁 mock/banners.ts
  → MSW로 가짜 데이터 정의

📁 mock/browser.ts
  → setupWorker로 핸들러 등록

📁 api/banner.api.ts
  → axios 기반 fetchBanners 함수 정의

📁 hooks/useMain.ts
  → fetchBanners 호출, 전역 상태로 저장

📁 components/common/Banners/
  → useMain()에서 받아온 banners 렌더링 (슬라이더 구성)

✅ 4. 각 단계 상세 설명

1) 📁 /src/mock/banners.ts

  • MSW로 실제 API가 없어도 가짜 배너 데이터를 반환할 수 있도록 정의합니다.
  • /banners 엔드포인트 응답을 가로채서 응답을 반환합니다.
// MSW 핸들러
export const banners = http.get('http://localhost:9999/banners', () => {
  return HttpResponse.json(bannersData);
});

2) 📁 /src/api/banner.api.ts

    • axios 기반 유틸 requestHandler를 사용해 공통화된 방식으로 데이터를 요청합니다.
export const fetchBanners = async (): Promise<Banner[]> => {
  return await requestHandler<undefined, Banner[]>('get', '/banners');
};

※ requestHandler는 axios를 래핑한 유틸 함수

3) 📁 /src/hooks/useMain.ts

  • 메인에서 필요한 모든 데이터를 한 번에 패칭합니다 (신간, 리뷰, 배너 등).
  • UI는 오직 이 훅만 사용해 banners 상태만 참조합니다.
const [banners, setBanners] = useState<Banner[]>([]);

useEffect(() => {
  fetchBanners().then(setBanners);
}, []);

4) 📁 components/common/Banners/

  • Banners.tsx: 슬라이더 전체 구성
  • BannerItem.tsx: 단일 배너 렌더링
  • banner.css.ts: 스타일을 Vanilla Extract로 정의하여 타입 안전성과 확장성을 확보

🎨 슬라이드 배너 동작 구성 요소

  • Banners.tsx에서는 setInterval을 통해 자동 순환 슬라이드를 구현했고,
  • 좌우 이동 버튼(ChevronLeft, ChevronRight)과 하단 Dot Indicator 클릭 이벤트도 제공합니다.
  • BannerItem.tsx에서는 overlay, title, description을 포함한 시각적 표현을 담당합니다.

🎯 왜 이렇게 설계했는가?

목적 어떻게 해결했는가
백엔드 없이 개발 병렬 진행 MSW(Mock Service Worker)로 API 응답 모킹
컴포넌트 간 결합도 최소화 useMain에서 상태 관리하고, 컴포넌트는 상태만 받아서 사용
유지보수 가능한 폴더 구조 역할별로 api, mock, hooks, models, components를 나눔
디자인 시스템과 확장성 확보 스타일은 Vanilla Extract로 작성 → Tailwind 스타일 추상화 가능

✅ 4. 데이터 흐름 정리

단계 설명
① Mock 핸들러 정의 /banners 요청을 가로채고 가짜 데이터 응답
② MSW 등록 핸들러를 setupWorker에 연결
③ API 요청 함수 작성 fetchBanners()에서 axios 요청
④ 커스텀 훅 사용 useMain()에서 데이터를 불러오고 상태 저장
⑤ 컴포넌트 사용 메인 화면에서 banners.map(...) 형태로 UI 렌더링

🧪 결과 및 장점 요약

  • 실제 API가 없어도 개발 가능 → 개발 효율성 향상
  • 하나의 useMain 훅으로 데이터 접근 일원화 → 코드 구조 간결
  • 컴포넌트는 재사용 가능 → UI 확장성 확보
  • Vanilla Extract 스타일로 타입 안정성 보장 → 버그 감소

✅ 마무리

이번 구조는 Mock → API 전환이 용이하고, 역할별 폴더 분리로 가독성과 유지보수가 뛰어난 구조입니다.
이런 구조를 통해 API 개발이 지연되거나 불완전한 상황에서도 프론트 개발을 병렬적으로 진행할 수 있고,
이후 실제 API로 교체할 때는 fetch 함수만 바꿔주면 되기 때문에 유지보수에도 유리한 구조입니다.

💭 회고

• 새롭게 알게 된 점

  • MSW를 활용하면 실제 서버 없이도 API 요청 흐름을 그대로 재현할 수 있어, 초기 프론트 개발 생산성이 매우 높다는 것을 체감했다.
  • 기존에는 axios 요청을 직접 컴포넌트 안에서 사용했는데, 유틸로 추상화된 requestHandler를 쓰니 코드 재사용성과 유지보수가 훨씬 좋아졌다.
  • Vanilla Extract는 Tailwind처럼 직관적인 클래스 설계는 어렵지만, 타입 보장과 구조화된 스타일 작성에 강점이 있다.

• 어렵게 느껴졌던 부분

  • 배너 슬라이더를 직접 구현하면서 자동 순환, 좌우 버튼, 하단 indicator, CSS transform 계산까지 신경 쓸 게 많았다.
  • CSS 오버레이와 transition 속성이 예상대로 동작하지 않아 디버깅에 시간이 걸렸다.
  • 타입스크립트와 Vanilla Extract를 결합하면서 타입 추론이 깨질 때 어떤 구조로 스타일을 export해야 하는지 고민이 많았다.
