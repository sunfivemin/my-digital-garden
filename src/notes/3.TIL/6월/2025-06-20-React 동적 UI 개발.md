## 📍 주제 1: React 프로젝트 생성 방식의 변화
React 공식 문서에 따르면, 이제 `create-react-app`은 더 이상 권장되지 않는다. 
대신 아래 두 가지 방식이 추천된다:
### ✅ 1. Next.js (App Router 기반)
서버사이드 렌더링(SSR)까지 고려한 풀스택 프레임워크로, 가장 권장되는 방식
```bash
npx create-next-app@latest
```
- React 기반의 **풀스택 프레임워크**
- 페이지 기반 라우팅 (app/, page.tsx)
- SSR/SSG/ISR 지원
- SEO 최적화와 빠른 초기 렌더링
- **Vercel 배포**와 찰떡궁합

### ✅ 2. React Router + Vite
CSR 중심의 빠른 프론트엔드 앱 구축에 적합
```bash
npm create vite@latest
```
- CRA보다 **10~20배 빠른 빌드**
- ESBuild 기반의 모듈 번들링
- React Router를 사용해 SPA 구성
- 빠른 로컬 개발 환경, 가벼운 번들 크기

## 💡 CRA, Vite, Next.js 비교
|**항목**|**CRA**|**Vite**|**Next.js**|
|---|---|---|---|
|공식 지원|❌ 사용 지양|✅|✅|
|빌드 속도|느림|매우 빠름|중간|
|라우팅|수동 설정|수동 설정|자동 (폴더 기반)|

|추천 용도|❌ 더 이상 사용 X|빠른 SPA|풀스택 앱|

## 📍 주제 2: npm, npx, yarn, pnpm 차이
### ✅ 1. npm (Node Package Manager)
- Node.js 설치 시 기본으로 제공
- 패키지를 설치하고 관리하는 가장 기본적인 도구
```bash
npm install react
npm run dev   # scripts 실행
```
- package.json, package-lock.json 생성
- 가장 널리 사용되고, 대부분의 튜토리얼은 npm 기준으로 작성

---

### ✅ 2. npx(npm exec)
- npm에 **포함된 실행 도구**
- **전역 설치 없이도 패키지를 바로 실행**할 수 있음
- 예: create-react-app, create-next-app, eslint, vite 등 설치 없이 1회 실행
```bash
npx create-react-app my-app
npx vite
```
즉, npx는 “설치하지 않아도 잠깐 실행할 수 있다”는 점에서 npm과 다름

---

### ✅ 3. yarn
- Facebook이 만든 패키지 매니저 (npm보다 안정성과 속도를 개선하기 위해 탄생)
- 특징:
	- 설치 속도 빠름 (병렬 설치)
	- yarn.lock으로 일관된 버전 관리
	- workspaces로 모노레포 구성에 적합

```bash
yarn install
yarn dev
```
CRA, Next.js 등 대부분 프레임워크와 호환됨

---

### ✅ 4. pnpm(Performant npm)
- 최신 트렌드의 패키지 매니저 (점점 많이 사용됨)
- **하드 링크** 방식으로 디스크 공간 절약 (여러 프로젝트에서 중복 설치하지 않음)
- 가장 빠르고 가볍다고 평가받음
```bash
pnpm install
pnpm dev
```
 특히 **모노레포**나 대규모 프로젝트에서 성능 차이가 확연히 남

---

### 🤔 같이 써도 될까?
| **도구 조합**   | **추천 여부** | **이유**                                                    |
| ----------- | --------- | --------------------------------------------------------- |
| npm + npx   | ✅         | 기본 조합. 공식 튜토리얼에서 사용됨                                      |
| npm + yarn  | ❌         | **lockfile 충돌** (npm은 package-lock.json, yarn은 yarn.lock) |
| npm + pnpm  | ❌         | 캐시 방식 및 설치 구조 다름. 예기치 못한 충돌 가능                            |
| yarn + pnpm | ❌         | 마찬가지로 비추천. 둘 다 **독립적인 생태계** 운영                            |
✅ **하나만 정해서** 프로젝트에 쭉 사용하는 것이 **가장 안정적**

---

### 🔧 언제 어떤 걸 쓰면 좋을까?

| **상황**                | **추천 도구** |
| --------------------- | --------- |
| 입문자, 튜토리얼 따라하기        | npm, npx  |
| 빠른 속도와 안정적 버전 관리 원할 때 | yarn      |
| 디스크 절약 + 빠른 설치 + 모노레포 | pnpm      |

## 📍 주제 3: React 폴더 구조
대규모 프로젝트에서는 폴더 구조를 어떻게 구성하느냐가 생산성과 유지보수에 큰 영향을 준다. 이 글에서는 실무에서 자주 사용하는 구조를 소개한다.

## 1. `pages/`
**📌 라우트에 대응하는 페이지 컴포넌트를 담는 폴더**
- react-router 또는 Next.js 기반 프로젝트에서 **URL 경로**에 직접 대응되는 컴포넌트들을 관리
- 각 컴포넌트는 전체 화면의 레이아웃을 구성하고 내부에 필요한 하위 컴포넌트를 포함
- 컨테이너 역할을 하기도 하며, 상태 관리나 비즈니스 로직이 포함될 수 있음

```
pages/
  ├── Home.tsx
  ├── Login.tsx
  └── BookDetail.tsx
```

## 2. `components/`
**📌 재사용 가능한 UI 컴포넌트들을 모아둔 폴더**
- 버튼, 카드, 모달 등 **여러 페이지에서 공유 가능한 단위 UI**
- 보통 props를 받아 시각적 요소를 담당하며, 상태는 외부에서 제어
- 페이지와 직접 연결되기보다는 **작고 재사용성 높은 단위**들로 구성

```
components/
  ├── Button.tsx
  ├── Modal.tsx
  └── BookCard.tsx
```

## 3. `utils/`
**📌 유틸리티 함수, 헬퍼 함수들을 담는 폴더**
- 날짜 포맷팅, 숫자 변환, 정렬 함수 등 **비즈니스 로직과 무관한 순수 함수들**
- 테스트 용이하며, 재사용성이 높은 기능들로 구성

```
utils/
  ├── formatDate.ts
  ├── generateId.ts
  └── calculateDiscount.ts
```

## 4. `hooks/`
**📌 커스텀 훅(Custom Hook)을 저장하는 폴더**
- useAuth, useModal, useFetch 등 **반복되는 로직을 추상화**하여 재사용
- React의 상태 관리나 효과 로직을 모듈화할 수 있어 코드 간결성 유지에 유리

```
hooks/
  ├── useAuth.ts
  ├── useDebounce.ts
  └── useScrollToTop.ts
```


## 5. `model/`
**📌 타입 정의(TypeScript)나 데이터 모델을 정의하는 폴더**
- API 응답 타입, 내부에서 사용하는 인터페이스, Enum 등 타입 관련 코드
- 전역에서 사용하는 **공통 타입을 정리해 타입 안전성을 확보**

```
model/
  ├── user.ts
  ├── book.ts
  └── api.ts
```

## 6. `api/`
**📌 백엔드 API와 통신하는 fetcher, axios 인스턴스를 정의하는 폴더**
- axios, fetch를 통해 서버와 데이터 통신
- 각 API 기능별로 함수로 분리하여 모듈화 → 유지보수 편함

```
api/
  ├── auth.ts
  ├── book.ts
  └── instance.ts (axios.create 설정)
```

## 📍 주제 3: Vite + TypeScript 프로젝트에서 타입 검사 스크립트 설정하기

Vite 프로젝트를 사용하면서도 타입 안정성을 위해 타입 검사 툴인 tsc (TypeScript CLI) 를 명시적으로 실행할 필요가 있다. 이를 위해 package.json에 typecheck 스크립트를 설정할 수 있다.

### ✅ 스크립트 추가 방법
package.json의 scripts에 다음을 추가한다:
```json
"scripts": {
  "dev": "vite",
  "build": "tsc -b && vite build",
  "lint": "eslint .",
  "preview": "vite preview",
  "typecheck": "tsc --noEmit --skipLibCheck"
}
```

| **옵션**         | **설명**                                    |
| -------------- | ----------------------------------------- |
| --noEmit       | JS 파일을 생성하지 않고 타입 검사만 수행                  |
| --skipLibCheck | node_modules 내부 .d.ts는 검사하지 않음 (검사 속도 향상) |

### ✅ 실행 방법
```json
npm run typecheck
```

### 🧠 왜 필요한가?
- Vite는 자체적으로 빌드시 타입 검사를 수행하지 않기 때문에, 타입 검사를 생략하면 런타임 오류를 놓칠 수 있음
- ESLint는 타입 관련 이슈를 완벽하게 잡아주지 않기 때문에 tsc와 함께 사용하는 것이 권장됨

## 📍 주제 4: tsconfig.json 상세 설정 분석
Vite 기반 프로젝트에서는 tsconfig.json을 커스터마이징하여 빌드 속도, 타입 안정성, 모듈 처리 방식을 조절할 수 있다. 이번에 사용한 설정을 기준으로 항목별 설명을 정리해보자.
```json
{
  "compilerOptions": {
    "tsBuildInfoFile": "./node_modules/.tmp/tsconfig.app.tsbuildinfo",
    "target": "ES2020",
    "lib": ["ES2020", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "skipLibCheck": true,
    "moduleResolution": "bundler",
    "allowImportingTsExtensions": true,
    "verbatimModuleSyntax": true,
    "moduleDetection": "force",
    "noEmit": true,
    "jsx": "react-jsx",
    "strict": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "erasableSyntaxOnly": true,
    "noFallthroughCasesInSwitch": true,
    "noUncheckedSideEffectImports": true
  },
  "include": ["src"]
}
```

| **옵션**                                                                       | **설명**                                                  |
| ---------------------------------------------------------------------------- | ------------------------------------------------------- |
| target: "ES2020"                                                             | 트랜스파일 타깃 JS 버전 (async/await 등 최신 문법 지원)                 |
| lib                                                                          | DOM 조작 및 최신 JS API 사용 가능하도록 관련 라이브러리 포함                 |
| module: "ESNext"                                                             | 최신 모듈 시스템 사용 (ESM)                                      |
| skipLibCheck: true                                                           | node_modules 내 타입 체크 생략 → 빌드 속도 향상                      |
| noEmit: true                                                                 | JS 파일은 출력하지 않고 타입 체크만 수행                                |
| jsx: "react-jsx"                                                             | React 17+ JSX 변환 방식 사용 (JSX import 생략 가능)               |
| strict: true                                                                 | 모든 strict 타입 검사 활성화 (strictNullChecks, noImplicitAny 등) |
| noUnusedLocals, noUnusedParameters                                           | 안 쓰는 변수나 매개변수 감지 → 클린 코드 유도                             |
| moduleResolution: "bundler"                                                  | Vite 등 번들러의 모듈 방식에 맞춘 모듈 해석                             |
| allowImportingTsExtensions                                                   | .ts 확장자를 명시적으로 import 가능                                |
| verbatimModuleSyntax                                                         | import/export를 코드 그대로 유지                                |
| moduleDetection: "force"                                                     | 모듈로 인식하도록 강제화 (side-effect 없는 파일 포함 방지)                 |
| erasableSyntaxOnly, noFallthroughCasesInSwitch, noUncheckedSideEffectImports | 정적 분석 강화를 위한 고급 옵션                                      |

### **✅** tsconfig.json 확장 구성
```json
{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" }
  ]
}
```
- 이 설정은 프로젝트를 **빌드 단위로 분리**할 수 있게 해줌
- tsconfig.app.json과 tsconfig.node.json을 각각 독립적으로 관리 가능
- 대규모 모노레포나 서버+클라이언트 구조에서 유용

## 💭 회고
• **새롭게 알게 된 점**
- React 공식 문서에서 **create-react-app이 더 이상 권장되지 않는다는 사실**이 인상 깊었음.
- npm, npx, yarn, pnpm 각각의 차이를 명확히 이해했고, **프로젝트마다 하나의 도구만 일관되게 사용하는 게 중요**하다는 점을 알게 됨.
- tsconfig.json은 단순히 타입 설정만 하는 것이 아니라, **빌드 성능이나 유지보수성에도 영향을 주는 핵심 파일**이라는 점을 새삼 느꼈음.
- vite에서는 타입 검사(tsc)가 자동으로 실행되지 않기 때문에, typecheck 스크립트를 별도로 작성해야 함.

• **어렵게 느껴졌던 부분**
- tsconfig.json 내 설정 항목들이 처음엔 생소해서 **각 옵션이 실제로 어떤 역할을 하는지 직관적으로 이해하기 어려웠음**.
- npm, pnpm, yarn을 혼용하면 lock 파일 충돌이나 패키지 캐시 오류가 생길 수 있다는 점을 몰랐고, 실제로 오류가 났을 때 원인 찾기가 어려웠음.
- Vite와 CRA의 차이를 단순히 “빠르다”라고만 생각했는데, **모듈 방식, HMR 방식, 타입 지원 등 전반적인 설계 철학이 다름**을 이번에 학습하며 깨달음.
