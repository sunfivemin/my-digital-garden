# 📘 2025-07-15 TIL
# 📘 쿠버네티스 입문 - 왜 모든 개발자가 배워야 할까?

안녕하세요! 오늘은 요즘 핫한 기술인 Kubernetes(쿠버네티스)에 대해 깊이 있게 공부해봤습니다. 

## 🤯 기존 시스템의 한계점을 먼저 이해해보자

### 모놀리식 아키텍처의 문제점

예전에는 모든 기능을 하나의 거대한 애플리케이션에 때려박는 **모놀리식 아키텍처**를 많이 사용했습니다. 예를 들어, 쇼핑몰을 만든다면:

하나의 거대한 애플리케이션├── 사용자 관리 ├── 상품 관리  
├── 주문 처리 ├── 결제 시스템 └── 배송 관리

이렇게 모든 게 하나로 묶여있으니까 문제가 많았죠:

- 하나 고치려면 전체를 다시 배포해야 함
- 특정 기능만 확장하기 어려움
- 한 부분에 버그가 생기면 전체 시스템이 다운
- 기술 스택을 바꾸기 어려움

### 마이크로서비스 아키텍처의 등장

그래서 나온 게 **마이크로서비스 아키텍처(MSA)**입니다. 큰 애플리케이션을 작은 서비스들로 쪼개는 거예요:

[사용자 서비스] ←→ [상품 서비스] ←→ [주문 서비스] ←→ [결제 서비스] ←→ [배송 서비스] 
↓ ↓ ↓ ↓ ↓ DB_User DB_Product DB_Order DB_Payment DB_Delivery

이렇게 하면 좋은 점이 많아요:

- **독립적인 개발**: 각 팀이 자기 서비스만 집중 개발
- **기술의 자유도**: 사용자 서비스는 Node.js, 결제는 Java 이런 식으로 각기 다른 기술 사용 가능
- **확장성**: 주문이 많이 들어오면 주문 서비스만 늘리면 됨
- **장애 격리**: 결제 서비스에 문제가 생겨도 상품 조회는 정상 작동

하지만 여기서 새로운 문제가 생겨요. 서비스가 수십, 수백 개가 되면 관리가 너무 복잡해지는 거죠. 그래서 등장한 게 바로 **Kubernetes**입니다!

## ☸️ Kubernetes가 뭐길래 이렇게 난리인가?

### 쿠버네티스는 '컨테이너 오케스트레이션' 도구

쉽게 말해서, **수많은 컨테이너들을 자동으로 관리해주는 똑똑한 매니저**라고 생각하면 됩니다.

예를 들어, 쇼핑몰에 갑자기 주문이 폭증했다고 해봅시다. 기존에는 개발자가 직접:

1. 서버 상황 모니터링
2. "어? 주문 서비스가 느려지네?"
3. 수동으로 서버 추가
4. 로드밸런서 설정 변경
5. 새벽에 깨서 장애 대응...

이런 식으로 하나하나 손으로 해야 했어요. 하지만 쿠버네티스가 있으면:

개발자: "주문 서비스는 최소 3개, 최대 10개까지 자동으로 늘려줘" 쿠버네티스: "네, 알겠습니다! 부하 보고 알아서 조절할게요~"

이렇게 자동으로 해줍니다. 진짜 마법 같죠?

## 🚀 쿠버네티스의 4가지 슈퍼파워

### 1. 컨테이너 밸런싱 (Container Balancing)

"주문 서비스 3개 띄워줘!" 하면 알아서 서버들에 고르게 분산해서 배치해줍니다.

### 2. 트래픽 로드 밸런싱 (Traffic Load Balancing)

여러 개의 동일한 서비스가 있으면 트래픽을 골고루 나눠서 보내줘요. 한 서버만 죽도록 일하는 일이 없죠.

### 3. 동적 수평 스케일링 (HPA; Horizontal Pod Autoscaling)

이게 진짜 신기한 기능이에요. CPU 사용률이 70%를 넘으면 자동으로 서버를 늘리고, 한가해지면 다시 줄여줍니다.

평소: 주문서비스 × 2대 점심시간(급증): 주문서비스 × 8대 자동 증설 새벽(한가): 주문서비스 × 1대 자동 축소

### 4. 오류 복구 (Error Recovery)

서버가 죽으면? 걱정 없어요. 쿠버네티스가 "어? 이 서버 응답 안 하네?" 하고 즉시 새로운 서버를 띄워줍니다. 24시간 무인 병원 같은 느낌이에요.

## 🏗️ 쿠버네티스 클러스터 해부학

### Control Plane (대장님들이 사는 곳)

쿠버네티스 클러스터의 두뇌 역할을 하는 곳이에요:

- **API Server**: 모든 요청의 접수창구. "새 서비스 배포해주세요~" 하면 여기서 받아요
- **etcd**: 클러스터의 모든 정보를 저장하는 데이터베이스. 쿠버네티스의 기억장치
- **Controller Manager**: "음... 서비스 3개 띄우라고 했는데 지금 2개밖에 없네? 하나 더 띄워야겠다" 이런 걸 담당
- **Scheduler**: "새 서비스를 어느 서버에 배치할까?" 하고 최적의 위치를 정해주는 배치 전문가
- **Cloud Controller Manager**: AWS, GCP 같은 클라우드와 소통하는 번역관

### Worker Node (실제로 일하는 곳)

진짜 애플리케이션들이 돌아가는 곳이에요:

- **kubelet**: 각 노드의 관리자. "새 컨테이너 띄워야겠네" 하고 실제로 실행시켜주는 담당자
- **kube-proxy**: 네트워크 트래픽을 적절히 라우팅해주는 교통정리 담당
- **Container Runtime (CRI)**: Docker 같은 컨테이너를 실제로 실행시키는 엔진

이걸 그림으로 보면:

```
Control Plane (지휘본부)
     ↓ 명령
```

┌─────────────────────────┐ │ Worker Node 1 │ Worker Node 2  
│ ┌─────┐ ┌─────┐ ┌─────┐ │ ┌─────┐ ┌─────┐ │ │Pod 1│ │Pod 2│ │Pod 3│ │ │Pod 1│ │Pod 2│ │ └─────┘ └─────┘ └─────┘ │ └─────┘ └─────┘ └─────────────────────────┘

## 🔄 Pod가 태어나는 과정 (감동 스토리)

Pod가 생성되는 과정이 정말 재밌어요:

1. **개발자**: kubectl create deployment nginx --image=nginx (nginx 서버 하나 띄워줘!)
2. **API Server**: "네, 요청 접수했습니다!" → etcd에 기록
3. **Controller Manager**: "어? 새 배포 요청이 있네? Pod 하나 만들어야겠다"
4. **Scheduler**: "음... 어느 노드가 한가하지? 아, Node2가 좋겠네!"
5. **Node2의 kubelet**: "새 Pod 만들라는 지시를 받았습니다!" → Docker에게 컨테이너 실행 요청
6. **Docker**: "nginx 컨테이너 실행 완료!"
7. **kubelet**: "Pod 정상 작동 중입니다!" → API Server에 보고

이 모든 과정이 몇 초 안에 자동으로 일어나요. 진짜 신기하죠?

### 쿠버네티스의 선언적 사고방식

일반적인 프로그래밍은 "절차적"이에요:

```
1. 서버에 접속해라
2. nginx를 설치해라
3. 설정파일을 수정해라
4. 서비스를 시작해라
```

하지만 쿠버네티스는 "선언적"이에요:

```
"nginx 서버가 3대 돌아가고 있는 상태가 되어야 해"
```

그럼 쿠버네티스가 알아서 현재 상태를 확인하고 목표 상태로 만들어줍니다. 현재 2대만 있으면 1대를 더 띄우고, 4대가 있으면 1대를 줄이고... 이런 식으로요.

## 📦 쿠버네티스 오브젝트 가이드

### 기본 오브젝트들

**Pod**: 쿠버네티스의 가장 작은 단위

- 보통 컨테이너 1개 = Pod 1개
- 고유한 IP 주소를 가짐
- **중요**: Pod는 언제든지 죽을 수 있어요! (이게 핵심 개념)

Pod = 임시 숙소 컨테이너 = 임시 숙소에 사는 사람

**Namespace**: 리소스를 그룹으로 나누는 폴더 같은 개념

default/ # 기본 네임스페이스 ├── frontend/ # 프론트엔드 관련 ├── backend/ # 백엔드 관련  
└── monitoring/ # 모니터링 관련

**Volume**: 데이터를 저장하는 공간

- Pod가 죽어도 데이터는 살아있어야 하니까 필요해요

**Service**: Pod들에게 안정적인 접근 방법을 제공

- Pod IP는 계속 바뀌니까, 고정된 접점이 필요해요

### Deployment (실전에서 가장 많이 쓰는 것)

실제로는 Pod를 직접 만들기보다는 **Deployment**를 주로 사용해요:

yaml

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3  # nginx 서버 3대 띄워줘
  template:
    spec:
      containers:
      - name: nginx
        image: nginx:latest
```

Deployment의 장점:

- Pod가 죽으면 자동으로 새 Pod 생성
- 롤링 업데이트 지원 (무중단 배포)
- 쉽게 스케일링 가능

## 🏗️ 쿠버네티스 설치 옵션 가이드

### 학습/개발용 (로컬 환경)

- **Docker Desktop**: 가장 쉬움. 클릭 몇 번이면 끝
- **kubeadm**: 좀 더 본격적으로 배우고 싶을 때
- **minikube**: 가벼운 로컬 클러스터

### 실제 운영용 (클라우드)

- **AWS EKS**: 아마존에서 관리해주는 쿠버네티스
- **Google GKE**: 구글 버전 (쿠버네티스를 만든 회사라서 가장 완성도 높음)
- **Azure AKS**: 마이크로소프트 버전

### 회사 내부 서버 (온프레미스)

- **Red Hat OpenShift**: 기업용 쿠버네티스 플랫폼
- **SUSE Rancher**: 여러 클러스터를 관리하기 좋음

## 🛠️ 실습 준비: Docker Desktop으로 시작하기

오늘 실습에서는 Docker Desktop을 사용했어요. 설정 방법:

1. Docker Desktop 설치
2. 설정(⚙️) → Kubernetes → Enable Kubernetes 체크
3. Apply & Restart
4. 터미널에서 `kubectl get nodes` 실행해서 확인

정말 간단하죠? 이제 로컬에서도 쿠버네티스를 맘껏 실험해볼 수 있어요!

## 🤔 오늘 공부하면서 든 생각들

### CI/CD와의 연계성

쿠버네티스와 CI/CD 파이프라인의 조합이 정말 강력할 것 같아요:
코드 커밋 → 자동 빌드 → 도커 이미지 생성 → 쿠버네티스에 자동 배포
이 모든 과정이 자동화되면 개발자는 코드만 짜면 되고, 나머지는 시스템이 알아서 처리해주니까요.

### 앞으로 더 배워야 할 것들

- **kubectl 명령어**: 쿠버네티스와 소통하는 기본 도구
- **YAML 작성법**: 쿠버네티스 설정 파일 문법
- **모니터링**: Prometheus, Grafana 같은 도구들
- **보안**: RBAC, Secret 관리 등

## 🎯 오늘의 핵심 요약

1. **마이크로서비스 아키텍처**는 큰 애플리케이션을 작은 서비스들로 나누는 방식
2. **쿠버네티스**는 이런 작은 서비스들을 자동으로 관리해주는 플랫폼
3. **자동화의 끝판왕**: 스케일링, 로드밸런싱, 오류복구 모두 자동
4. **Pod는 언제든지 죽을 수 있다**: 이게 쿠버네티스 설계의 핵심
5. **선언적 구조**: "어떻게"가 아니라 "무엇을" 원하는지 선언하면 쿠버네티스가 알아서 해줌

처음엔 복잡해 보였는데, 하나씩 뜯어보니 정말 잘 설계된 시스템이라는 걸 느꼈어요. 특히 자동화된 관리 기능들이 개발자의 삶을 얼마나 편하게 만들어주는지 실감했습니다.

다음에는 직접 애플리케이션을 배포해보면서 실전 경험을 쌓아봐야겠어요! 🚀
